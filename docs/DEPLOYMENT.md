# Deploying mps-ai

Automatic on every green CI run on the default branch, and manually for a
rollback. The workflow is [`.github/workflows/deploy.yml`](../.github/workflows/deploy.yml);
the work happens in [`deploy/deploy-ai.sh`](../deploy/deploy-ai.sh).

## Why this exists

Until this deploy path landed, `mps-ai` had CI and nothing else:

- no deploy workflow — `gh workflow list` showed only `CI — Lint · Test`;
- **zero repository secrets**, while the backend and WhatsApp repos both have
  `HOST`, `USERNAME`, `SSH_KEY`;
- `docker-compose.snippet.yml`, which asks an operator to paste a service into
  `/opt/myptstudio/docker-compose.yml` by hand — a step that is never triggered
  by a push and is easy to leave undone;
- a CI branch filter on the real default branch
  (`claude/session-01dcjf1c88rf5nfdukc-o1vv0m-5l89cs`), so a deploy copied from
  the sibling repos' `main` filter would never have fired anyway.

The result was observable in production: `https://myptstudio.com/ai/health`
redirected to `/login` and nothing listened on `127.0.0.1:4100`.

## What runs where

```
GitHub Actions
  CI — Lint · Test  ──success──▶  Deploy mps-ai to VPS
                                     │ SSH (HOST/USERNAME/SSH_KEY)
                                     ▼
VPS /opt/myptstudio/mps-ai          git checkout --detach <sha>
  deploy/deploy-ai.sh               docker compose -p mps-ai build ai
                                     │
                                     ▼
                         myptstudio-ai  (127.0.0.1:4100)
                                     │  shared ERP Docker network
                                     ▼
                         myptstudio-backend:5000
```

- Compose project `mps-ai` from `deploy/compose.ai.yml`, deliberately **not**
  merged into `/opt/myptstudio/docker-compose.yml`: that file is unversioned on
  the box and belongs to the ERP. Only the Docker network is shared.
- The container joins the network resolved from the running
  `myptstudio-backend` (not a guessed name), so ERP calls stay on the host.
- `GIT_SHA` is baked into the image and returned by `GET /health`. The deploy
  fails unless `/health` echoes the exact commit that was built.
- On a failed start, unhealthy container, or SHA mismatch, the script retags the
  previously deployed image (`mps-ai:previous`) as `mps-ai:current` and
  recreates the container. On a first deploy there is no previous image, so the
  service is stopped rather than left serving an unverified build.

## Repository secrets (required before the first automatic deploy)

Add these in **Settings → Secrets and variables → Actions**. Use the same
values already configured in `619-erp-backend` / `619-erp-whatsapp`; secret
values cannot be read back or copied by tooling, so an operator must add them.

| Secret | Purpose |
| --- | --- |
| `HOST` | VPS address |
| `USERNAME` | SSH user |
| `SSH_KEY` | Private key with deploy access to `/opt/myptstudio` |

Until these exist, the deploy job fails immediately at the SSH step and nothing
on the box is touched. That is the intended failure mode, not a deployment.

## Box environment (already present, presence-checked only)

`/opt/myptstudio/.env` must contain:

| Key | Notes |
| --- | --- |
| `OPENROUTER_API_KEY` | Same account/key the ERP uses |
| `SERVICE_AUTH_SECRET` | **Must equal the ERP's value.** Never generated by this deploy |
| `AI_ALLOWED_ORIGINS` | Exact browser origin(s), e.g. `https://myptstudio.com` |

The script checks that each key is non-empty and never prints, copies or
rotates a value. Optional overrides: `AI_PRIMARY_MODEL`, `AI_FALLBACK_MODEL`,
`AI_QUOTA_MODE`, `AI_LOG_LEVEL`, `AI_RATE_LIMIT_MAX`, `AI_MEM_LIMIT`,
`AI_ERP_BACKEND_URL`.

## Manual operations

```bash
# Deploy a specific commit (also the rollback path):
gh workflow run deploy.yml -f sha=<40-char-sha>

# On the box, by hand:
bash /opt/myptstudio/mps-ai/deploy/deploy-ai.sh <sha>

# What is deployed, and what is running:
cat /opt/myptstudio/.mps-ai-deployed-sha
curl -s http://127.0.0.1:4100/health
docker inspect --format '{{.State.Health.Status}}' myptstudio-ai
```

Rollback targets must be commits that contain `deploy/deploy-ai.sh` (any commit
after this deploy path landed). Older commits cannot be deployed by this
workflow.

## One-time nginx step (not automated here)

The intended public route already exists in
`619-erp-backend/infra/nginx/myptstudio.conf`:

```nginx
location /ai/ {
    proxy_pass http://127.0.0.1:4100;
    include /etc/nginx/snippets/myptstudio-proxy.conf;
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;
    proxy_buffering off;
}
```

It is not live on the box yet — `https://myptstudio.com/ai/health` currently
answers `307` to `/login`, which is the frontend, not this service. The deploy
does not edit nginx or reload it: that changes routing for the whole site and
belongs to an operator.

The prefix block forwards `/ai/...` unchanged on purpose: this service serves
the agent at `/ai/client-agent/*`. Health lives at the root (`/health`), so it
is deliberately not public and the deploy verifies it over loopback. If a
public liveness check is wanted, add an exact match *before* the prefix block:

```nginx
location = /ai/health {
    proxy_pass http://127.0.0.1:4100/health;
}
```

After the first successful deploy:

1. Apply the `location /ai/` block to the live vhost (or deploy the updated
   `myptstudio.conf` the same way the backend does); add the exact-match health
   block if you want one.
2. `sudo nginx -t && sudo systemctl reload nginx`.
3. Confirm `curl -s http://127.0.0.1:4100/health` on the box returns
   `{"status":"ok","service":"mps-ai","sha":"<deployed sha>"}` and, if the
   exact-match block was added, the same body over
   `https://myptstudio.com/ai/health`.

## First deploy checklist

1. Merge the deploy change to the default branch.
2. Add the three repository secrets.
3. Confirm the three keys above exist in `/opt/myptstudio/.env`.
4. Confirm nothing else publishes port 4100 (the script refuses with a named
   container if something does).
5. Let CI pass on the default branch, or run the workflow manually.
6. Apply the nginx block, reload, and load the AI panel through
   `myptstudio.com`.

## Failure semantics

- CI fails → `workflow_run` has conclusion `failure` → job skipped.
- Missing secrets → SSH step fails before any remote command runs.
- Missing box env key → script exits before building.
- Build fails → old container and `mps-ai:current` untouched.
- New container unhealthy or serving the wrong SHA → automatic rollback and a
  non-zero exit; the workflow is red and the marker file is not advanced.
